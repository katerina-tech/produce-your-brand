# Behavioural evaluation

Regenerate with:

```bash
cd backend && uv run python scripts/run_eval.py --write
```

## What this measures, and what it deliberately does not

This evaluates the **decision layer** — which single field the workflow asks about next, and how a supplier scores against a brief. That is where this product's correctness claims actually live, and all of it is pure Python (`app/services/completeness.py`, `app/services/matching.py`): no model call, no network, no clock read (`today` is injected). So every row below is exact and reproducible, and the harness can run in CI on every change rather than billing a provider per row.

The table is **generated by the harness, not written by hand**, and `--write` refuses to update this file while any case fails — so a committed result cannot drift away from what the code does.

Two things this is not:

- **It is not an extraction eval.** Turning free text into a typed `ProductionRequirement` is the one step that genuinely needs a live model, so it is verified separately (below) rather than mocked and scored here, which would only measure the mock.
- **It is not a quality judgement.** It checks that stated rules hold, not that the weighting is *right*. Whether "material compatibility is worth 20 points" is good product design is a question for user evidence — see the README's [Product hypothesis](../README.md#product-hypothesis) — not for this table.

## Coverage

| Category | Cases |
|---|---|
| Complete brief proceeds without interrogation | 1 |
| Incomplete brief asks for exactly one field, in priority order | 2–6 |
| Non-blocking gaps do **not** trigger a question | 7–8 |
| Deadline feasibility, including past and impossible dates | 9–12 |
| Material compatibility, including an unsupported material | 13–14 |
| `null` scored differently from `false` (unknown is not "no") | 12, 14, 15 |
| Hard gates: structural impossibilities excluded, never ranked | 16–17 |
| Quantity against the supplier's published MOQ | 18 |
| The funnel over the real dataset | 19 |

Cases 12, 14 and 15 are the ones worth reading closely: an unconfirmed capability scores *partial credit with a risk flag*, while an explicit refusal is a hard gate (16). Conflating the two would either hide a real blocker or silently discard a viable partner.
